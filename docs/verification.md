# Verification record and limits

This is an experimental integration of pinned upstream CKB. Passing a finite fixture suite is not proof of consensus equivalence, and no independent production security audit is claimed.

## Reproduce

```sh
./scripts/prepare.sh
cargo fmt --all -- --check
cargo clippy --locked -p ckb-wasm-verifier --all-targets --no-deps -- -D warnings
cargo test --locked -p ckb-wasm-verifier
cargo build --locked -p ckb-wasm-verifier --bin verify
npm ci
npm test
npm run typecheck
./scripts/build-wasm.sh
npm run test:wasm
npm run test:differential
npx playwright install chromium
npm run test:browser
```

`fixtures/*.json` contain `{request, expected}`. They are generated by the native wrapper using the same pinned CKB verifier, not hand-written success stubs. The differential suite separately invokes the compiled native CLI for each request and compares actual results against the actual WASM engine, including cycles, fee, errors and group membership. Group array order is normalized because upstream hash-map iteration order is not meaningful. This comparison checks host/platform consistency; it does not independently prove that our context wrapper includes every required rule.

Regenerate only when intentionally reviewing a behavior change:

```sh
cargo run -p ckb-wasm-verifier --example generate-fixtures -- fixtures
```

The baseline fixtures exercise full lock execution, lock plus type execution, selected lock/type groups, dep-group expansion, cycle exhaustion, nonzero script exit, malformed ELF, version/shape/capacity rejection, duplicate inputs/dependencies, maturity/since, incomplete context and inconsistent metadata. Adversarial host-width cases are described beside the compatibility patches.

## Limits

- The corpus is synthetic and small. It is not a replay of historical mainnet blocks or a comprehensive upstream conformance suite.
- Complex DAO withdrawal transitions, every syscall family, TYPE_ID lifecycle, spawn/exec process trees and all historical hardfork boundaries need broader fixtures.
- Native comparison includes a binary built from unmodified upstream submodules, but uses the same integration wrapper. A separate full-node oracle and known historical transactions would provide stronger evidence.
- JSON/snapshot size and memory consumption need application-level limits. Cycle limits bound VM execution, not parsing, context allocation or every setup cost.
- The API trusts the developer's external context. It cannot authenticate headers, cell data, extensions, spent status, ancestry or proposal inclusion.
- Browser execution should use the Worker interface. Workers may be terminated by the caller; the direct synchronous WASM call has no cooperative cancellation API.

## Local execution record (2026-11-12)

- Rust 1.95.0 native check, formatting, tests and Clippy were run.
- 33 transaction fixtures run through the real WASM engine, plus an initialization/invalid-request check.
- Live differential comparison against native, including an unmodified-upstream native binary.
- 11 JavaScript boundary/Worker-protocol tests and TypeScript declarations checked.
- WASM release generated with wasm-bindgen 0.2.105 and WASI SDK 34 clang (only as C compiler, still targeting bare wasm32-unknown-unknown).
- The local environment could not launch Chromium because a required local socket operation was unavailable. Managed-browser access also could not reach the isolated local server. No local real-browser pass is claimed; the committed CI workflow runs the real offline Worker test in Chromium. Check the exact commit's workflow result.
